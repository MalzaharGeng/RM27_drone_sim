## 被测对象与环境

源码为 `8313a4a342374d867518e8b4de97cfdabecfe7c0`，基于 PX4 v1.17.0 的地面翻正接入；本仓库在 `PX4-Autopilot/` 收录其完整快照，原始版本及依赖见 [源码清单](../../PX4_SOURCE_MANIFEST.json)。测试使用同源 WSL 已构建 SITL 可执行文件，不是实机固件。

环境为 WSL Ubuntu 26.04、Gazebo Sim 10.5.0、PX4 instance 7。每次使用独立 rootfs、Gazebo partition 和进程组；没有解锁或操作硬件。测试机型为 PX4 标准 x500，用于隔离飞控回正链路，**不是 Harrier 原场地验收**。

默认参数保留：高/低油门 0.20/0.10，进入角 75°，停油角 60°，出力上限 3 s，进度阈值 3°/0.8 s。测试只启用 `FLIP_EN`、切换模式及施加制造初始侧翻的外力；外力撤去后等待 5 s，再进入回正模式。

torque600 撤去外力后稳定在约 79.92°，满足进入角；模块日志实测估计倾角约 79.7–79.9°，安全条件为 OK。随后进入出力阶段，因未获得规定进展而失败。物理真值最终仍约 79.92°，没有达到正立标准，不能登记为翻正通过。

本轮 HEARTBEAT 采样未捕获第三次短暂的翻正模式；ULog `vehicle_status` 记录了 nav_state=16，控制台也记录了 Ramp/Hold 和退出。模式是否进入以组合证据判定，不能把心跳漏采误写成模式拒绝。

## 执行链证据

- 三次运行接收的 Gazebo `command/motor_speed` 均为零；torque600 的监视窗口收到 3501 条消息，未产生回正转速命令。
- 当前 `GZMixingInterfaceESC` 仅消费普通混控输出；`flip_recovery_control` 的停机、换向、恢复时序接在 DShot 实机驱动，Gazebo 后端尚无对应消费者。这是源码中可确认的接入缺口。
- 模块真实走到 Ramp/Hold/Failed，不能把“仿真执行器未接入”表述为“规划器永远无法启动”，也不能据此判断硬件推力或电调能力。
- 本轮 ULog 缺少 `flip_recovery_control/status` 数据集，listener 也未得到对应样本；该段证据不完整。状态变化来自模块日志，姿态、落地、未解锁及模式来自 ULog，转速命令来自 Gazebo 独立订阅。
- 没有以外部直接电机出力、`FLIP_OUT_DIRECT=1` 或真值替换估计器来绕过缺口。
